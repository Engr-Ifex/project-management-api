### Architecture facts discovered (not obvious, cost time)

- **Mongoose applies schema defaults on LOAD, not only on create.** Measured
  against real MongoDB: `$unset isVerified` on a document, then `findById` →
  `isVerified === false` (the default), even though the raw document genuinely
  has no such key. This inverted the design: the first version used
  `default: false` + "undefined means grandfathered", which would have marked
  **every pre-existing account unverified** and locked them out of creating a
  workspace or accepting an invitation. Final: **`default: true`**, with
  `isVerified: false` set **explicitly in `registerUser`** — the single place an
  unverified account is created. `migrateUserVerification.js` backfills but is
  **not required for correctness**.
- **`sanitizeUser` already emitted `isVerified`** while the model had no such
  field — it serialised as `undefined` and `JSON.stringify` dropped it. The
  field had been anticipated.
- **The Resend SDK does not throw for API rejections** — it resolves with
  `{ data: null, error }`. Both that and a thrown transport failure must be
  handled, or a rejected message looks like success.
- **Zod validation errors carry the full path** (`body.token`), not the bare
  field. `client/src/lib/api/client.ts` strips the `body.`/`params.`/`query.`
  prefix in `normalizeFieldError`. Server tests must assert `body.token`.
- **Express 5 leaves `req.body` undefined** unless a body parser populated it,
  and `express.json()` only parses with a body + JSON content type. A
  `z.object({})` body therefore rejects a bodyless POST with "expected object,
  received undefined". Use `.optional()`.
- **`createUser` in `tests/helpers/factories.js` sets `isVerified: true`**, and
  the schema default is `true` — so the ~200 tests that build fixtures directly
  keep working. Only `registerUser` creates an unverified account.

### The verification policy, and why it is only two routes

An unverified account may sign in and read but **cannot obtain workspace
membership**. Enforced on exactly two routes — `POST /workspaces` and
`PATCH /invitations/:token/accept` — because those are the only two ways
membership is created, and every nested resource sits behind
`requireWorkspaceMember`. Two guards cover the whole surface by construction.
`403`, not `401` (401 would tear down a perfectly good session).

### Traps hit and fixed

- **Redirect race.** Sending registration to `/verify-email` while
  `RequireAnonymous` still sent authenticated users to `/workspaces` produced a
  coin-flip redirect — the exact hazard documented in `routes/guards.tsx`. Fix:
  one shared `postAuthDestination(state, user)` in `lib/auth/redirect.ts`, used
  by the guard, `Login` and `Register`. **Any future post-auth destination
  decision must go through it.**
- **Session revocation needs a >1s gap in tests.** The middleware allows a
  one-second `iat` tolerance, so issuing a token and resetting within the same
  second leaves the token valid *correctly*. The test sleeps 1200 ms.
- **`tests/helpers/setup.js` forces `CLIENT_URL` to `http://localhost:5173`**
  unless `CLIENT_URL_TEST` is set. Booting the harness with `CLIENT_URL=…` is
  silently overridden — pass `CLIENT_URL_TEST` instead.
- **Raw-collection queries need an ObjectId.** `Model.collection.findOne({ _id:
  'string' })` never matches.
- **A throwaway express app needs `cookieParser()`** or `req.cookies` is
  undefined and `authenticate` 500s.

### Dev harness

`client/dev/boot-real-api.mjs` now also serves a **dev mailbox** on
`127.0.0.1:5051` (node:http, not express — `express` is not resolvable from
`client/`). It exposes the test suite's recording email transport so browser
harnesses can follow real emailed links; the server stores only a digest, so the
token is otherwise unrecoverable. **Harness only** — `server/app.js` has no such
route, and an endpoint returning verification tokens would be an
account-takeover primitive. `qa.mjs` and `verify-fixes.mjs` were updated to
confirm their seeded account through it, since registration is now unverified.

### Deliberate trade-off

`forgot-password` reports a provider failure to **nobody** — the response is
identical for a known address, an unknown address and a failed send. A distinct
failure would occur only for addresses that *do* have accounts, reintroducing the
enumeration oracle the endpoint exists to prevent. It is logged at error level,
so it is not silent; it is just not visible to the caller. Registration and the
authenticated resend endpoint report failures honestly.
