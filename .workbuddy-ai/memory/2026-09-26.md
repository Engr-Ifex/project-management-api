# 2026-09-26 — Frontend integration audit + closing the image/jpg regression

## 1. Closed a regression I introduced last session

`AVATAR_ALLOWED_MIME_TYPES` includes `'image/jpg'` (not a registered type, but
clients send it). My `CONTENT_FOR_MIME_TYPE` map did NOT include it, and
`isContentAllowedForMimeType` refuses a MIME type with no rule — so a **genuine
JPEG avatar sent as `image/jpg` was rejected with 400**. Fixed by adding the
rule, and closed the class of bug: the two allow-lists (attachments vs avatars)
are separate, and my drift test only covered the attachment one. Now both are
covered, in both directions (no allowed type without a rule; no rule without an
allowed type). Exported `AVATAR_ALLOWED_MIME_TYPES` for the test.

Verified discriminating: removing the rule fails 2 tests.

## 2. Frontend integration map → `client/API-INTEGRATION.md`

Written into `client/` so the backend stays untouched. Covers the 16 requested
areas: all 82 endpoints by group, request bodies, path params, auth, roles,
permissions, errors, and the pagination/filter/sort contract.

**Method matters here:** I extracted the inventory from `docs/openapi.json`
programmatically (a throwaway script) rather than reading routes by hand — the
spec is generated from the route table AND the routes' own Zod validators, so
it is the authoritative contract, not a hand-written summary.

### Things the frontend will trip over (all verified, not assumed)

- **Auth is a cookie** (`accessToken`, httpOnly, SameSite=Strict). Needs
  `credentials: 'include'`; session probe is `GET /users/profile`; **no refresh
  token**; same-site only.
- **Id shape is split**: `User` and `Workspace` serialize `id`, everything else
  `_id`.
- **`members` is optional on project list/detail** — omitted for callers
  without project access (the privacy fix from last session).
- **Boolean query params are the strings `"true"`/`"false"`**, not booleans.
- **Comment editing is author-only**; deletion honours the moderate override.
- **Attachments download through an authenticated endpoint** — a plain `<img
  src>` 401s.
- **Project lifecycle is workspace-level**, so a project owner cannot rename or
  archive their own project.
- **404 is used where 403 would leak existence.**

### Two OpenAPI schema gaps found (reported, NOT fixed — backend is frozen)

The spec is verified against the route table, but response **schemas** are
hand-authored, and two understate reality:

1. `POST …/invitations` — `Invitation` schema omits `token`, but the API returns
   it (verified by probe: `data.invitation.token`, 64-char hex). It is the ONLY
   way an invitee can accept, because **there is no email delivery**.
2. `GET …/projects/:projectId/labels` — schema says `data = { labels }`; the
   service returns `{ labels, pagination }` and it accepts `page`/`limit`.

Both are flagged prominently in the map so a type generated from the spec is
corrected by hand. Left in place deliberately: the user said do not modify the
backend.

## Gotchas

- **Probe, don't infer, when a hand-authored schema is involved.** I nearly
  documented "the token is returned" from reading the model; the spec said
  otherwise. A 6-line throwaway test settled it in seconds. Do that whenever the
  generated spec and the code could disagree.
- **Read the drift test's scope.** Mine asserted the attachment allow-list only,
  which is exactly why `image/jpg` slipped through. When two lists feed one
  validator, assert on both.

## 3. Closed the design system's last open item: real-browser verification

`client/DESIGN-SYSTEM.md` §9 ended with "**Not verified:** rendering in a real
browser, and the responsive behaviour at each breakpoint." That is now verified
and the section is rewritten. Nothing in `client/src` changed — this was a
verification pass, not a code change.

Verified against the **production build** (`client/dist`, static server on
`127.0.0.1:5173`) driven by headless Chrome over CDP:

- whole page renders at 1440 × 6169 px; every showcase section present
- `≥ 1024px` fixed 240px sidebar; `768–1024px` drawer + hamburger;
  `< 640px` (390) drawer, single column, table scrolls inside its own wrapper
- modal opens/escapes with focus returning; dropdown menu opens; toasts stack
- measured in the live page: `document.fonts` → both Geist faces `loaded`,
  `body` is `14px`, `td` has `font-variant-numeric: tabular-nums`
- six requests, all 200 except `/favicon.ico` → **404 — the project has no
  favicon**. Cosmetic, but a browser always asks; worth adding.

### The technique is the reusable part

`agent-browser` is **not installed**, and `agent-browser install` pulls ~500 MB
of Chromium — impossible on this disk. But Chrome is already on the machine, so
the whole job is: launch it with `--remote-debugging-port`, then drive it over
CDP with **Node 22's built-in `WebSocket`** (no npm packages at all).

- `Page.captureScreenshot` **without** a clip = viewport; **with**
  `clip: {x, y, width, height}` + `captureBeyondViewport` = any rectangle. That
  is how the 6169px page was cut into five readable 1440 × 1400 slices — a single
  full-page PNG is unreadable once the viewer downscales it.
- `--window-size` alone only ever captures the viewport, so a "tall window"
  screenshot is a dead end. Use `Emulation.setDeviceMetricsOverride` + clip.

### Three traps that cost real time

- **`Input.dispatchMouseEvent` coordinates are viewport-relative.** The
  dropdown trigger sat at `y = 5366` in a 900px viewport, so the click landed on
  nothing and the menu silently never opened. `scrollIntoView({block:'center'})`
  first, *then* read the rect. A silent no-op looks exactly like a broken
  component.
- **Radix `DropdownMenu` opens on `pointerdown`, not `click`.** A synthetic
  `el.click()` opens a `Dialog` fine but does nothing for a menu. Dispatch
  `mousePressed`/`mouseReleased` via CDP instead.
- **Headless Chrome profiles eat disk.** Two profiles reached **112 MB**, and
  with C: already at 99% the box hit **100% full / 238 MB free** mid-task. Delete
  the `--user-data-dir` after the run; never leave it in the repo. This is very
  likely the original "not enough space" blocker.

`.tmp-shots/` is now in the root `.gitignore` so the scratch can never be
committed.

## 4. Phase 3 — the frontend is now an application, not a design system

Phase 2 shipped tokens and primitives with no router, no API client and no auth.
Phase 3 added all of it: **~30 new files** under `client/src`. `tsc --noEmit`
clean, `vite build` 4.4 s, route-level code splitting (each screen its own chunk
instead of one 493 kB bundle). Documented in the new `client/README.md`.

### The decision that made everything else work: a dev proxy

The server's `CORS_ORIGINS` is **unset**, so cross-origin browser requests are
refused outright — and the session cookie is `SameSite=Strict`, so it would not
be sent to another origin either. Rather than edit the backend (frozen), `/api`
is proxied by Vite and the client's base URL is the relative `/api/v1`. The
browser then talks to its own origin and both problems vanish. Same proxy wired
for `preview`.

### Probed rather than assumed

Three shapes the contract does not state, all settled by reading the server:

- **`subtasks` is embedded** (`type: [subtaskSchema]`), not a reference — so it
  is always present and always objects. **`labels` is a reference**, populated to
  `{_id, name, color}`. Two different shapes in one document.
- **`GET /workspaces/:id` returns `members` UNPOPULATED** (`members[].user` is a
  raw ObjectId). That is ideal: the `role` sits on the member entry, so the
  caller's workspace role costs nothing extra. The members *screen* calls
  `GET …/members`, which does populate names and avatars.
- The task service populates `createdBy` / `assignee` / `labels` / `archivedBy`.

### Bug I wrote and caught: `useMutation` could not report success

`run` originally returned `TResult | undefined`. But **every DELETE and archive
endpoint succeeds with no body**, so `TResult` is legitimately `undefined` on
success — a successful delete and a failure were indistinguishable, and
`if (result !== undefined)` read success as failure. Changed to a discriminated
outcome (`{ok:true,data} | {ok:false,error}`) and updated every call site.
Worth remembering: "returns undefined on success" is a real API shape, and a
`T | undefined` return type silently collapses it.

### Verification

`/` → redirects to `/login`, login renders, title `Sign in · Project Management`,
React mounted (27 nodes in `#root`). `/design` still renders at **6169 px** —
identical to the Phase 2 measurement, which is how the `AppShell` change was
regression-checked. `/favicon.ico` **404 is fixed** (SVG favicon declared).

**All twelve authenticated screens were then rendered too** — against a
dependency-free stand-in API (`client/dev/mock-api.mjs`, `npm run mock`) on
:5000, which is what the preview proxy already targets. The real backend was not
running, and starting it would write to the production Atlas cluster in
`server/.env`, which is not a thing to do uninvited. Every route rendered with
**zero failed requests** and its own correct document title.

Two results worth more than the page count:

- The sidebar **unread badge** renders, so `useUnreadCount` polls and paints.
- On a task, the comment the signed-in user **authored** offers Edit + Delete;
  a colleague's offers **Delete only**. That is `canEditComment` (author-only, no
  override) versus `canDeleteComment` (author *or* `comment:moderate`) visibly
  diverging — the exact distinction the contract calls out, confirmed on screen
  rather than in a type.

**What that proves and what it does not.** It proves each screen mounts and
renders against the payload *shapes* in `API-INTEGRATION.md`. It does **not**
prove the real API returns those shapes — the mock is a claim about the API
written from the contract and the server's models, not evidence of it. No screen
has been exercised against live data. The README says exactly this rather than
implying full coverage.

### Gotchas

- **A green UI run against a mock is not API verification.** Worth stating
  explicitly wherever the result is reported, because it is very easy to let
  "12/12 screens passed" read as "the integration works".
- **`127.0.0.1` ≠ `localhost` on Windows.** Vite binds `localhost` → IPv6 `::1`,
  so `curl http://127.0.0.1:5173` returned `HTTP 000` while the server was
  running fine. Use `localhost`. Added to the `headless-browser-verify` skill.
- **The sandbox blocks a build tool from emptying its own output dir.** Vite's
  `prepareOutDir` died with `SAFE_DELETE_BULK_CONFIRM_REQUIRED` on
  `dist/assets` (1009 files). An environment guard, not a code error — delete the
  regenerable `dist/` yourself and rebuild. Also added to the skill.
- `client/` has **no ESLint config**, so `npm run lint` fails. `tsc` covers
  unused locals/params but not hook-dependency rules. Left for a follow-up.

## 5. Empty/error states, and a real bug in my own tooling

### The empty and no-results states are verified

`MOCK_MODE=empty` / `MOCK_MODE=error` added to `client/dev/mock-api.mjs`, which
empties only the **top-level** arrays — deliberately not `workspace.members`,
because emptying that would change the caller's role and turn "an empty list"
into a different screen entirely.

`/workspaces` → "No workspaces yet"; the projects table → "No projects yet in
this workspace." with no filter active. The copy is the *empty* variant, not the
*no-results* variant — which is the distinction the design system makes a point
of, holding on screen.

### I had a disk-filling bug in the browser-verify skill

The run crashed on a transient CDP `-32000 Unable to capture screenshot`, and
**the Chrome profile was left behind** — twice, 16 MB and 4 MB. Root cause: the
`exit` handler cannot `await`, and on Windows the OS keeps handles on the profile
after the process is killed, so the immediate `rmSync` threw and the error was
swallowed. On a nearly-full disk that leaks 100 MB+ *per run*.

Fixed three ways, each verified rather than assumed:
1. kill → wait 500 ms → retry the delete up to 6 times, warn loudly if it fails;
2. `uncaughtException` / `unhandledRejection` handlers that await cleanup then
   exit, so a crash cannot leak;
3. retry `captureScreenshot` (3×) and clamp clip height to ≥1 px.

Re-ran afterwards: **0 profiles before, 0 after.** Confirmed, not hoped.

### Two things I did NOT do, and why

- **Did not clear the npm cache.** It is the obvious win (8166 files), but
  `npm cache clean --force` was blocked by the sandbox's bulk-delete guard, and
  the cache lives in `AppData` — a no-go zone. I declined to escalate past a
  safety guard to delete from there. The user can run it themselves.
- **Did not delete `server/tests/tmp-probe.test.js`.** Despite the `tmp-` name it
  is the **evidence base for `API-INTEGRATION.md`** — it probes the documented
  claims against a real database. It is not a throwaway. But it imports no
  `assert`, so it runs on every `npm test`, prints ~40 `PROBE` lines and can
  never fail. Worth either asserting on it or moving it out of the `tests/*.test.js`
  glob; deleting it would destroy someone's verification record.

A brief arrived asking for the architecture in a specific shape. Most of it
already existed, but the **directory taxonomy did not**, and one item was a
genuine defect. Done with `git mv` so history follows the files, then a scripted

| Was | Now |
| --- | --- |

### The real defect: option lists copy-pasted four times

Task statuses were declared in the project layout, the tasks tab, the task detail
**and** as a re-export — so a status added server-side could be wired into one
screen and silently missing from the others. Now declared once in
`lib/constants/`.

Two judgement calls encoded there:

- **`*_FILTER_OPTIONS` are separate exports from the form lists.** A filter has a
  legitimate "all" state; a create form does not. One shared list makes it
  possible to accidentally *save* a task with status `"all"`.
- **`ASSIGNABLE_WORKSPACE_ROLE_OPTIONS` excludes `owner`**, and
  `ASSIGNABLE_PROJECT_ROLE_OPTIONS` excludes `owner` too — ownership is
  transferred or set at creation, never granted through a picker. One list for
  both would offer a choice the API rejects.

Also fixed: `NOTIFICATION_SCOPE_OPTIONS` typed as `string[]` widened the generic
on `SegmentedControl`, forcing a cast at the call site. Typed as a union
(`NotificationScope`) instead — fix the constant, not the caller.

### Forgot / reset password: checked, and deliberately NOT built

The brief said "if supported by the backend". It is not: `auth.routes.js`
registers exactly three routes (`register`, `login`, `logout`) and

work**, so none was created — and the omission is documented in
`client/README.md` and in the route table's header comment so nobody "fixes" it
by adding a dead page.
