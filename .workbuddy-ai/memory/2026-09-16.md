# 2026-09-16 — Fix: Mongoose ValidationError -> 400

Resolved the one open item carried forward from Phase 14: `ValidationError` was falling through to **500** because the global error middleware only mapped `CastError` and duplicate-key `11000`.

## Change
`src/middlewares/error.middleware.js` — added a `ValidationError` branch alongside the existing CastError/11000/MulterError blocks, in the same style. Nothing else touched; no other mapping altered.

- Status: **400** (a broken request payload is a client fault, not a server fault).
- Message: `'Validation failed'` — deliberately mirrors the Zod path in `validate.middleware.js`, so schema-level and request-level validation failures look identical to clients.
- `errors`: normalised to the standard `[{ field, message }]` array. Mongoose hands back an **object keyed by path**, which would otherwise have leaked a raw object into the response body.

## Detail worth remembering
Mongoose's `err.errors` is keyed by the **fully-qualified path**, while each issue's own `issue.path` holds only the **leaf**:
- top level: key `title`, `issue.path` `title`
- nested subdocument: key `storage.key`, `issue.path` `key`

The middleware therefore uses the **object key** (`field || issue.path`), so nested paths are reported as `storage.key` rather than an ambiguous bare `key` — consistent with the dotted paths Zod produces (e.g. `body.content`).

Also: `doc.validateSync()` **returns** the ValidationError, it does not throw — relevant for writing offline tests.

# 2026-09-16 (later) — Phase 15: DASHBOARD

## Pre-existing state (inspected first)
- **No dashboard/statistics code existed** — built from scratch.
- Read-authorization in this codebase is mixed: `GET .../projects` and `GET .../tasks` are guarded by `requireWorkspaceMember` only, while the newer modules (activities, labels, comments, attachments) use `requireProjectPermission('project:view')`. Followed the **newer, stricter** convention for the project dashboard.
- `Task.assignee` had **no index** — the one obvious gap the dashboard queries reveal.

## Schema facts that drove the design
- `Task`: status `todo|in_progress|in_review|completed|cancelled`, priority `low|medium|high|urgent`, `dueDate` (nullable), `assignee` (nullable), `estimatedTime` (unit-less Number), `isArchived`. **There is no `completedAt` on Task** — "completed" is `status === 'completed'`.
- `Project`/`Workspace`/`Task` have **`isArchived` only — no soft-delete field**. So for reporting, *archived === deleted*. This is the answer to "keep calculations accurate with archived/deleted records".
- `estimatedTime` has no unit in the schema; totals are reported in whatever unit the client writes (minutes by convention) and documented as such.

## Endpoints (2)
- `GET /workspaces/:workspaceId/dashboard` — guard: `authenticate + validate + requireWorkspaceMember + requireWorkspacePermission(VIEW_WORKSPACE)`
- `GET /workspaces/:workspaceId/projects/:projectId/dashboard` — guard: `authenticate + validate + requireWorkspaceMember + requireProjectPermission('project:view')`, optional `?upcomingDueDays=1..365` (default 7)

Deliberately only two, with **no duplicated figures**: the workspace dashboard reports project-level stats + the caller's own task stats; the project dashboard reports task-level stats + the caller's own stats in that project. No workspace-wide task rollup, which would just repeat the project dashboard.

## Aggregation logic
All figures computed in MongoDB — no documents loaded into application memory.
- **Workspace projects**: one `$match {workspace}` + `$facet{ archiveCounts, statusCounts }`. `statusCounts` re-matches `isArchived:false` so archived projects (which keep their old status) can't distort the distribution. `active = total - archived`; a missing `isArchived` counts as active, matching the schema default.
- **Project tasks**: `$match {project, isArchived:false}` + `$facet{ byStatus, byPriority, totals }` — one round trip for all three.
- **myTasks (project)**: `$match {project, assignee, isArchived:false}` + `$group`.
- **myTasks (workspace)**: `$match {assignee, isArchived:false}` → `$lookup` projects → `$unwind` → `$match {project.workspace, project.isArchived:false}` → `$group`. The `$lookup`+`$unwind` keeps the whole calculation in the DB (rather than loading project ids and using `$in`) **and** drops tasks whose project is gone, so a dangling ref can't inflate a total.

## Accuracy rules (applied consistently)
- Archived tasks excluded from every task figure.
- Archived projects counted only in `archived`, excluded from `byStatus`.
- **Completed and cancelled tasks are never overdue or upcoming** (shared `overdueCondition`/`upcomingCondition` expressions, bounded at both ends so the two never overlap).
- `completionPercentage = completed / (total - cancelled) × 100`, rounded to 1dp, 0 when the denominator is ≤ 0. Cancelled is removed from the denominator because it is not outstanding work; `cancelled` is also returned so a client can recompute.
- Bucket lists are read from the **Mongoose schemas** (`Model.schema.path(x).enumValues`) rather than duplicated in constants, so a new enum value can't leave the dashboard reporting a stale set. All buckets are zero-filled for a stable response shape.

## Indexes
Exactly **one** added: `Task { assignee: 1, isArchived: 1 }`.
It is the only genuine gap — myTasks would otherwise full-scan the entire tasks collection. Project/task dashboards already match `{project, isArchived}` and are served by existing `{project,isArchived,position}`, `{project,status}`, `{project,priority}`; and since those queries must read every live task of the project anyway, a `dueDate` index would not reduce work — so none was added (avoided speculative indexing).

## Reusable technique (worth remembering)
To verify aggregation pipelines without a reachable MongoDB: stub `Model.aggregate` and run the **real pipeline array** through a small in-memory evaluator over a fixture, comparing to hand-computed values. Assertions on pipeline shape alone would not have caught arithmetic errors. Key gotcha: treat only *plain* objects as operator expressions — `Date`/`ObjectId` are literals.

# 2026-09-16 (later) — Fix: `estimatedTime` contract = whole minutes

Corrects the `estimatedTime` line in the Phase 15 notes above: the unit is now fixed by contract, not client-defined.

## What inspection found (before changing anything)
| Layer | Non-negative | Integer | Unit documented |
|---|---|---|---|
| Zod **create** (`createTaskSchema`) | yes `.min(0)` | yes `.int()` | no |
| Zod **update** (`updateTaskSchema`) | yes `.min(0)` | yes `.int()` | no |
| Mongoose **model** | yes `min: [0,…]` | **no** | no |
| Dashboard response | — | — | no (comment said "unit-less number … minutes by convention") |
| `docs/` + `README` | no references at all — `docs/API.md` is a route table only, documents no request bodies |

Write sites: only `createTask` (spreads validated `taskData` into `Task.create`) and `updateTask` (`Object.assign(task, updateData)`). Verified by regex over the service that **no other operation assigns `estimatedTime`** — archive/restore/status/priority/assign/dueDate/startDate/subtasks all set named fields only.

So the API boundary was already correct (non-negative integer); the real gaps were the **model not enforcing integer** and the **minutes unit being undocumented**.

## Changes (3 files, all minimal)
1. `src/models/Task.js` — documented `estimatedTime` as whole minutes and added an integer validator:
   `validate: { validator: Number.isInteger, message: 'Estimated time must be a whole number of minutes' }`.
   The model now matches the Zod contract, so the rule holds even for a write that bypasses request validation. No schema *structure* change (no new field, no migration).
2. `src/validators/task.validator.js` — **behaviour unchanged** (both rules were already `.int().min(0)`); added comments stating the unit is whole minutes and that `0` is valid. The create/update rules were already identical, so no consolidation was needed.
3. `src/services/dashboard.service.js` — replaced the vague "unit-less number" comment with an explicit one, and added `unit: 'minutes'` inside the `estimatedTime` block so the payload states its own unit. Aggregation expressions untouched.

Note on the constraint "do NOT add a new `estimatedTimeUnit` or similar field": read as prohibiting a persisted Task field. `unit: 'minutes'` is a **response-only annotation** required by requirement 5 (response must identify the unit); nothing is stored. Flagged to the user in case they read it more strictly.
