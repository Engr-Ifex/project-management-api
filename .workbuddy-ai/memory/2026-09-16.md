# 2026-09-16 — Fix: Mongoose ValidationError -> 400

Resolved the one open item carried forward from Phase 14: `ValidationError` was falling through to **500** because the global error middleware only mapped `CastError` and duplicate-key `11000`.

## Change
`src/middlewares/error.middleware.js` — added a `ValidationError` branch alongside the existing CastError/11000/MulterError blocks, in the same style. Nothing else touched; no other mapping altered.

- Status: **400** (a broken request payload is a client fault, not a server fault).
- Message: `'Validation failed'` — deliberately mirrors the Zod path in `validate.middleware.js`, so schema-level and request-level validation failures look identical to clients.
- `errors`: normalised to the standard `[{ field, message }]` array. Mongoose hands back an **object keyed by path**, which would otherwise have leaked a raw object into the response body.

## Detail worth remembering
Mongoose's `err.errors` is keyed by the **fully-qualified path**, while each issue's own `issue.path` holds only the **leaf**:
- top level: key `title`, `issue.path` `title`
- nested subdocument: key `storage.key`, `issue.path` `key`

The middleware therefore uses the **object key** (`field || issue.path`), so nested paths are reported as `storage.key` rather than an ambiguous bare `key` — consistent with the dotted paths Zod produces (e.g. `body.content`).

Also: `doc.validateSync()` **returns** the ValidationError, it does not throw — relevant for writing offline tests.

# 2026-09-16 (later) — Phase 15: DASHBOARD

## Pre-existing state (inspected first)
- **No dashboard/statistics code existed** — built from scratch.
- Read-authorization in this codebase is mixed: `GET .../projects` and `GET .../tasks` are guarded by `requireWorkspaceMember` only, while the newer modules (activities, labels, comments, attachments) use `requireProjectPermission('project:view')`. Followed the **newer, stricter** convention for the project dashboard.
- `Task.assignee` had **no index** — the one obvious gap the dashboard queries reveal.

## Schema facts that drove the design
- `Task`: status `todo|in_progress|in_review|completed|cancelled`, priority `low|medium|high|urgent`, `dueDate` (nullable), `assignee` (nullable), `estimatedTime` (unit-less Number), `isArchived`. **There is no `completedAt` on Task** — "completed" is `status === 'completed'`.
- `Project`/`Workspace`/`Task` have **`isArchived` only — no soft-delete field**. So for reporting, *archived === deleted*. This is the answer to "keep calculations accurate with archived/deleted records".
- `estimatedTime` has no unit in the schema; totals are reported in whatever unit the client writes (minutes by convention) and documented as such.

## Endpoints (2)
- `GET /workspaces/:workspaceId/dashboard` — guard: `authenticate + validate + requireWorkspaceMember + requireWorkspacePermission(VIEW_WORKSPACE)`
- `GET /workspaces/:workspaceId/projects/:projectId/dashboard` — guard: `authenticate + validate + requireWorkspaceMember + requireProjectPermission('project:view')`, optional `?upcomingDueDays=1..365` (default 7)

Deliberately only two, with **no duplicated figures**: the workspace dashboard reports project-level stats + the caller's own task stats; the project dashboard reports task-level stats + the caller's own stats in that project. No workspace-wide task rollup, which would just repeat the project dashboard.

## Aggregation logic
All figures computed in MongoDB — no documents loaded into application memory.
- **Workspace projects**: one `$match {workspace}` + `$facet{ archiveCounts, statusCounts }`. `statusCounts` re-matches `isArchived:false` so archived projects (which keep their old status) can't distort the distribution. `active = total - archived`; a missing `isArchived` counts as active, matching the schema default.
- **Project tasks**: `$match {project, isArchived:false}` + `$facet{ byStatus, byPriority, totals }` — one round trip for all three.
- **myTasks (project)**: `$match {project, assignee, isArchived:false}` + `$group`.
- **myTasks (workspace)**: `$match {assignee, isArchived:false}` → `$lookup` projects → `$unwind` → `$match {project.workspace, project.isArchived:false}` → `$group`. The `$lookup`+`$unwind` keeps the whole calculation in the DB (rather than loading project ids and using `$in`) **and** drops tasks whose project is gone, so a dangling ref can't inflate a total.

## Accuracy rules (applied consistently)
- Archived tasks excluded from every task figure.
- Archived projects counted only in `archived`, excluded from `byStatus`.
- **Completed and cancelled tasks are never overdue or upcoming** (shared `overdueCondition`/`upcomingCondition` expressions, bounded at both ends so the two never overlap).
- `completionPercentage = completed / (total - cancelled) × 100`, rounded to 1dp, 0 when the denominator is ≤ 0. Cancelled is removed from the denominator because it is not outstanding work; `cancelled` is also returned so a client can recompute.
- Bucket lists are read from the **Mongoose schemas** (`Model.schema.path(x).enumValues`) rather than duplicated in constants, so a new enum value can't leave the dashboard reporting a stale set. All buckets are zero-filled for a stable response shape.

## Indexes
Exactly **one** added: `Task { assignee: 1, isArchived: 1 }`.
It is the only genuine gap — myTasks would otherwise full-scan the entire tasks collection. Project/task dashboards already match `{project, isArchived}` and are served by existing `{project,isArchived,position}`, `{project,status}`, `{project,priority}`; and since those queries must read every live task of the project anyway, a `dueDate` index would not reduce work — so none was added (avoided speculative indexing).

## Files modified (2)

# 2026-09-16 (later) — Phase 16: SEARCH / FILTERING / PAGINATION / SORTING

## Pre-existing state (inspected first)
Three different states coexisted:
- **Already paginated** (from Phases 12–14): notifications, activity, attachments — `{resource, pagination}`.
- **Plain arrays, no pagination**: workspaces, projects, tasks, comments, labels.
- Pagination was duplicated inline in 3 services; notification/activity validators each had their own local `paginationFields` copy.
- `GET /workspaces` had **no validator at all**.

## Two findings that shaped the design
1. **Express 5's default query parser is `simple`.** Probed it: `?status[$ne]=todo` arrives as the *literal string key* `status[t$ne]`, **not** a nested object. So MongoDB operator injection via nested query objects is structurally impossible here. Zod enums then reject operator-looking strings as a second layer.
2. **`hasPrevPage` vs `hasPreviousPage`.** The requirement lists `hasPreviousPage`, but `hasPrevPage` already exists and is live on notifications/activity/attachments. Requirement 3 permits "another consistent structure" and requirement 13 says don't break existing endpoints, so **`hasPrevPage` was kept** and this deviation is flagged to the user.

## Reusable utilities created (2 files)
- `src/utils/query.js` — `escapeRegex`, `buildSearchFilter`, `buildDateRange`, `buildSort`, `mergeFilters`, `findPaginated`. `findPaginated` is the single place list queries are run; it collapsed the duplicated `Promise.all([find…skip…limit, countDocuments])` from 3 services.
- `src/constants/query.js` — per-resource sort whitelists, searchable fields, default sorts and default orders, shared by **both** the validators (reject) and the services (build), so a whitelist can never drift from the query it constrains.
- `src/validators/query.validator.js` — shared `paginationQuery`, `sortQuery(fields)`, `searchQuery`, `booleanQuery`, `objectIdQuery`, `dateQuery`. Removed the two duplicated `paginationFields` copies.

## Injection / safety measures
- Sort fields resolved against a whitelist **twice** (Zod `z.enum` + `buildSort` re-check). `$where`-style values rejected.
- Search terms regex-escaped, so `.*` matches literally instead of everything (ReDoS/mass-match protection).
- Every filter is assembled field-by-field from validated primitives; no user string ever becomes a field name or operator.
- `OBJECT_ID_LIST_REGEX` validates a whole comma-separated id list, keeping `labels` a plain string.
- Cross-field refines reject contradictory input up front: `assignee` + `unassigned`, `dueDateFrom > dueDateTo`, `startDateFrom > startDateTo`, `deadlineFrom > deadlineTo`.

# 2026-09-16 (later) — Phase 17: SECURITY HARDENING

Full review of the backend, then fixes. **No new business features.**

## Vulnerabilities found

### High
1. **Private attachments were served publicly.** `app.js` mounted `express.static` on the whole `src/uploads` tree, which contains `src/uploads/attachments` — the private per-project store. Anyone could fetch `/uploads/attachments/<projectId>/<uuid>.<ext>` with no authentication, bypassing the authenticated download endpoint and all project authorization. **This was introduced in Phase 14** (the storage path sat under the static root despite the intent stated at the time).
2. **Invalid/expired JWTs returned HTTP 500.** `jwt.verify` throws `JsonWebTokenError` / `TokenExpiredError`, which the error middleware did not map. Every expired session looked like a server fault and clients could not detect "please log in again".
3. **No rate limiting anywhere** — login/register were brute-forceable.
4. **CORS wide open** — a bare `cors()` answered every origin with `*`.
5. **Weak/unvalidated JWT secret.** The live secret is 12 chars; there was no length check, and a *missing* secret only failed later as a 500 on first login. `BCRYPT_SALT_ROUNDS` missing would have become `NaN` and thrown inside bcrypt.

### Medium
6. **Login timing side-channel → account enumeration.** With an unknown email, `bcrypt.compare` was skipped entirely, so the response returned far faster than a wrong-password attempt.
7. **No token invalidation on password change** — stateless JWTs stayed valid for their full lifetime.
8. **`jwt.verify` did not pin the algorithm.**
9. **User `toJSON` did not strip `password`** (defence in depth; `select:false` was the only guard).
10. **No explicit body size limits** (relied on Express defaults).

### Low
11. `notFound.middleware.js` existed but was **empty and unregistered** → unknown routes returned Express's HTML 404.
12. `authorize.middleware.js` is dead code (never mounted).
13. Registration returns 409 for a taken email (enumeration) — kept, mitigated by rate limiting.
14. `req.project` / `req.projectMember` are set but never consumed, and are skipped on the workspace-admin bypass path.
15. `npm audit` could not be run (registry unreachable).

## `requireProjectPermission` review (explicitly requested)
**Verdict: the workspace owner/admin bypass is intentional and was left unchanged.**
- The gate is `hasPermission(req.workspaceMember.role, UPDATE_WORKSPACE)`, and `UPDATE_WORKSPACE` is held only by workspace **OWNER/ADMIN** (never MEMBER).
- `requireWorkspaceMember` runs first and resolves the workspace from `req.params.workspaceId`; `requireProjectPermission` then loads the project with `{_id: projectId, workspace: workspaceId}`. So the bypass is confined to the workspace in the URL — it **cannot cross workspaces** (verified by test).
- Residual authority: a workspace admin is effectively a superuser over every project in their workspace, including projects they are not a member of. That is the documented model; there is no "private project" concept. Changing it would weaken the permission architecture, which the brief forbids.
- Minor inconsistency noted: the early `return next()` skips the `req.project` / `req.projectMember` assignments. Harmless today (nothing reads them).
