## The pivotal judgement call: which side of the contradiction was wrong

The audit found the permission tables granting capabilities no route consults.
Deciding whether to change the guards or the tables was the whole task, and the
evidence pointed one way:

- `docs/API.md` §16 already said *"Project lifecycle is a workspace-level
  concern, so these routes require the `update_workspace` permission … rather
  than a project role"*, and §17 said adding/removing members needs workspace
  authority while changing a role needs project authority.
- `tests/authorization.test.js` asserts a plain workspace member gets **403** on
  a project read, with the message *"only owner/admin are elevated, not plain
  members"* — i.e. the intent is that project **content** needs a project role.
- Widening the guards would have **expanded** access, which the task forbade.

Conclusion: **the routes were right, the tables were wrong.** Removed the
unreachable grants; kept the names in `PROJECT_PERMISSIONS` as documented
`RESERVED` vocabulary.

## Read scope (the leak was real, and bigger than it looked)

Task/subtask reads needed only workspace membership while comments/labels/
attachments/dashboard/activity needed `project:view`. Task responses populate
`labels` with `name color`, so a workspace member could read label data through
the task route that the label routes refuse. Fixed by requiring `project:view`
uniformly; project **discovery** (list + record) stays at workspace level.
`client/` is EMPTY (0 files), so no frontend could break.

## Races — the mechanism matters more than the pattern

- **Ownership transfer**: Mongoose `$set`s only *modified paths*, so two
  concurrent transfers could set `members[1].role = owner` **and**
  `members[2].role = owner` → two owners. Fixed with one `$set` of both roles +
  `owner`, CAS on `owner`, using **two arrayFilters**.
- **Duplicate membership cannot use a unique index.** `{'members.user': 1}`
  unique enforces uniqueness *across documents* — it would forbid a user from
  joining a second workspace. The invariant is intra-document, which no MongoDB
  index can express. Conditional update is the only mechanism. (The task
  suggested a unique index here; it is not expressible — say so.)
- **Task `position` duplicates are deliberately tolerated** — `position` is an
  ordering hint, and a unique index would turn a benign collision into a failed
  request. Added `_id` as the final sort key so the order is total.
- Only ONE transaction, in `acceptInvitation`. Everything else lives in a single
  document where one update is already atomic.

## The test double had to be fixed first

The in-process store is the only DB available, so it must apply operators the
way MongoDB does or the concurrency tests prove nothing. Four real fidelity
bugs found and fixed (all in the double):

1. **`$ne`/`$nin` on an array path** were evaluated per element, so
   `{'members.user': {$ne: id}}` was true for almost every array — it would have
   made the new guard look broken in tests while being correct against MongoDB.
2. `$push` / `$addToSet` unsupported.
3. `$set` with `arrayFilters` unsupported (needed for the ownership swap).
4. `$push` did not assign a subdocument `_id`; `$pull` compared by equality so a
   condition document matched nothing.

# 2026-09-19 (later) — Phase 6 completed: index audit

The one phase I had short-changed. Twelve single-field indexes were **prefixes of
existing compound indexes**, so each was costing a write on every insert/update
while serving no query the compound could not:

`workspaces.owner` · `projects.workspace` · `tasks.project` ·
`taskcomments.{task,project,author}` · `attachments.{project,task,comment}` ·
`notifications.recipient` · `labels.project` · `projectactivities.project`

**Prefix redundancy is provable, not measurable** — if `{a:1,b:1}` exists then
`{a:1}` can never be the better choice for any query. So no `explain()` is
needed and no query plan can invalidate the conclusion. That is the line I drew:
I removed what is *provably* redundant and only **reported** what merely *looks*
unused (`{isArchived:1}` ×3, `{isDeleted:1}`, `{isRead:1}`, `attachments.uploader`,
`projectactivities.workspace`) — calling those unused needs query-plan analysis
against a real database, which does not exist here.

**Removing a schema declaration does NOT drop the index.** Mongoose only ever
creates. So the code is clean but an existing database still carries all twelve
until someone drops them — hence `src/migrations/dropRedundantIndexes.js` +
`npm run migrate:drop-indexes`, idempotent (IndexNotFound code 27 = skip), and
deliberately NOT run here because `.env` points at the real Atlas cluster and
running it would be destructive. Syntax-checked with `node --check` only.

`tests/indexes.test.js` (18 tests) derives redundancy from the index definitions
themselves, so it cannot rot like a snapshot. **Verified discriminating**: re-adding
`attachments.{project:1}` fails with `{"project":1} is a prefix of
{"project":1,"createdAt":-1}`. It also asserts `members.user` is NOT globally
unique — so nobody "fixes" the duplicate-member race by adding an index that would
forbid a user from joining a second workspace.

Final state: **308 tests / 64 suites / 308 pass**, lint 0/0, format clean,
`docs:verify` 82 = 82.
