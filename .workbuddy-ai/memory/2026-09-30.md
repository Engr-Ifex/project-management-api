## Workspaces area — verified against the running API; 3 client bugs fixed

Verified item "6 · Workspaces" end to end. **Three real client bugs found and
fixed**; the area is otherwise complete (list, create, edit, members, roles,
transfer ownership all work, and there is no standalone details view — the
workspace's own settings live under `/workspaces/:id/settings`, confirmed by the
route table).

1. **Switching lost the section** (`components/WorkspaceMenu.tsx`). The menu
   navigated to `/workspaces/<newId>` unconditionally, so switching from
   `/workspaces/a/projects` dropped you on the new workspace's *dashboard* —
   despite the component's own doc comment saying it "must preserve the *section*
   the user is in". Fixed by deriving the section from the current pathname and
   rebuilding the href. Depth *below* a section is deliberately dropped
   (`/workspaces/a/projects/p/tasks/t` → `/workspaces/b/projects`), because a
   project id from one workspace cannot exist in another. The section is taken
   from the path, not a hardcoded list, so it cannot drift from the route table.
   Verified live for every section: dashboard, projects, members, notifications,
   settings, and a deep project route.

2. **Archiving dumped the user onto an error page** (`pages/Settings.tsx`). After
   a *successful* archive the handler called `reloadWorkspace()`, but an archived
   workspace is invisible to the membership guard — `GET /workspaces/:id` answers
   **404** by design (pinned in `tests/workspace.test.js`, "An archived workspace
   is invisible to the normal membership guard") — so the page was immediately
   replaced by "Workspace not found". Now it navigates to `/workspaces`, matching
   what deleting a workspace already did.

3. **`Select` silently dropped `aria-label`** (`components/ui/Select.tsx`).
   `SelectProps` never declared it, and TypeScript permits a hyphenated attribute
   on a component without checking it against the props type — so
   `<Select aria-label="New owner">` compiled cleanly and did nothing. Both
   comboboxes on the Members screen (`Role for …`, `New owner`) had
   `aria-label: null` and `aria-labelledby: null`, i.e. no accessible name.
   Declared the prop and forwarded it to the trigger; verified the names now
   resolve.

All three: `tsc --noEmit` clean, no console errors, no failed requests.

### KNOWN GAP — restore is unreachable, and it is an API-level gap

**A workspace can be archived but never restored through the UI.** Not a client
coding error, and not fixable client-side:

- `GET /workspaces` hardcodes `isArchived: false`
  (`workspace.service.js` `getUserWorkspaces`), and its documented params are
  `page,limit,sortBy,order,search` — **no `isArchived`**, unlike `GET …/projects`
  and `GET …/tasks`, which both accept it.
- `GET /workspaces/:id` 404s when archived (deliberate; pinned by a test).
- `PATCH /workspaces/:id/restore` requires an **archived** workspace
  (`requireArchivedWorkspaceMember`).

So no read endpoint ever returns an archived workspace, and the restore endpoint
requires one. Consequences in the client, both **dead code**:
`WorkspaceList.tsx`'s `isArchived` "Archived" badge (the list never contains an
archived workspace) and `Settings.tsx`'s "Restore workspace" button (the page
404s before it can render). Verified: the API restore itself works (HTTP 200 when
called directly), so only reachability is broken.

Fix needs a product decision: mirror Projects/Tasks by letting `GET /workspaces`
honour an `isArchived` query param, then add the filter + restore affordance.
**Not done** — it changes the documented API contract. Reported to the user.

## FIXED — workspace restore is now reachable (the gap above)

Closed the gap reported in the previous entry. **Backend + client, mirroring how
Projects and Tasks already do it.** Contract change, so the docs were regenerated.

**Backend**
- `src/validators/workspace.validator.js` — `workspaceListSchema` gains
  `isArchived: booleanQuery('isArchived').optional()`, exactly as
  `project.validator.js` does.
- `src/services/workspace.service.js` — `getUserWorkspaces` now uses
  `isArchived: query.isArchived ?? false`. **The `?? false` default is what keeps
  this backward compatible**: omitting the param still returns live workspaces
  only, which the test suite confirms.
- `docs/openapi.json` regenerated (`npm run docs:generate`) — the spec now lists
  `isArchived` on `GET /api/v1/workspaces` with `enum ["true","false"]`.
  `npm run docs:verify` → "Documentation matches the implementation."

**Client**
- `lib/constants/workspace.ts` — `WORKSPACE_ARCHIVE_FILTER_OPTIONS`
  ('Active workspaces' / 'Archived only'), mirroring the project list.
- `pages/WorkspaceList.tsx` — the archived filter, a **Restore** action per
  archived row, and a `ConfirmDialog`. Two details that mattered:
  - The row was a single `<button>`, so the Restore control **could not be nested
    inside it** (invalid HTML, and the click would bubble into navigation). The
    `<li>` became a flex row with the navigable button as `flex-1` and Restore as
    a sibling.
  - Ownership per row is read from the list payload's own `members[].role` — no
    extra request. (The `user` there is an unpopulated id, which is fine: `refId`
    handles it, and the *role* is what is needed.)
  - The empty state distinguishes "archived-only and none" from "search matched
    nothing", instead of showing "no results" for both.

**Verified end to end against the running API**
- Omitted param → archived workspace absent; `isArchived=true` → present.
- Browser: filter shows the archived workspace (and hides active ones); Restore →
  confirm → gone from the archived list, back among active; empty state reads
  "No archived workspaces". No console errors.
- `tsc --noEmit` exit 0. Screenshot `.tmp-shots/ws-archived-view/slice-01.png`.

**Deliberate leftover:** `Settings.tsx`'s "Restore workspace" branch is now
unreachable in *both* directions (the page can never load an archived workspace).
Left in place rather than deleted — it is correctly guarded by
`workspace?.isArchived`, so it becomes live again if the detail route ever stops
404ing on archived workspaces. It is now redundant, not wrong.
