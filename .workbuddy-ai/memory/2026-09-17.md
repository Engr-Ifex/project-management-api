# 2026-09-17 — Phase 18: TESTING

Built the automated test suite from scratch. **No testing framework existed** (`tests/` was empty, `npm test` was a placeholder that exited 1).

## Framework chosen
- **`node:test` + `node:assert/strict`** — built into Node 22, zero config, native ESM, no transpilation.
- **`supertest` 7.2.2** — real HTTP against the real Express app.
- **`mongodb-memory-server` 11.2.0** — throwaway real MongoDB, isolated from the app database.

## The central problem: no database was reachable
Three separate blockers, all environmental:
1. The Atlas URI in `.env` is unreachable.
2. **C: is 100% full (29 MB free)** — `mongodb-memory-server` failed with `ENOSPC` mid-download. This also made the download appear to crawl (~90 KB/s) because writes were retrying.
3. Downloading to E: (17 GB free) fixed the disk problem, but the binary is **509 MB** and the link runs at ~70 KB/s → ~2 hours. Not completable in-session.

No `mongod` exists anywhere on the machine (checked PATH, `Program Files`, services, port 27017).

## Data-layer strategy (the key design decision)
`tests/helpers/setup.js` selects a backend via `TEST_DB`:
- `auto` (default) — real DB if a **cached mongod binary** is found, else the in-process store
- `mongodb` — require a real DB, fail loudly
- `memory` — force the in-process store

It checks for a cached binary **before** calling `MongoMemoryServer.create()`, because a missing binary triggers a huge download mid-run. Never hangs.

`tests/helpers/memoryStore.js` (700+ lines) is an in-process Mongoose replacement: real schemas, defaults, casting, validation, `toObject`, document methods, and **the real pre-save hooks** (so password hashing is genuinely exercised). Only the query transport is faked.

**This store is a test double, not a database.** It must never be presented as equivalent to running against real MongoDB. Running with `TEST_DB=mongodb` closes the gap.

## Store-fidelity bugs found and fixed (all in the double, not the app)
Each one produced a *false* test failure until fixed:
1. **`isNew` never flipped after a save.** Real Mongoose sets it false on first save; the User hook only stamps `passwordChangedAt` when `isNew === false`, so token invalidation silently never happened in tests. Fixed by calling `$__reset()` + clearing `isNew`.
2. **`select('+password')` was treated as an inclusive projection**, dropping email/name — so the next `save()` persisted a user with no email. Fixed: `+field` is *additive*; the schema's own `select: false` is the baseline projection.
3. **`save()` replaced the whole row**, wiping fields excluded by a projection. Mongoose updates only changed paths → changed to a merge.
4. **`findOneAndUpdate` was missing entirely.** A stale comment claimed the codebase never uses it — but it is used **5 times** (project update, task archive/restore). Implemented as a chainable + awaitable query with `populate` support.
5. **No ObjectId casting.** With a real driver a malformed id throws `CastError` → HTTP 400; the store just found nothing → 404. Added `assertCastable` so tests assert the *true* behaviour. It must skip operator wrappers (`{$ne: id}`) — my first version threw on those.

## App bugs found by the tests
1. **JWT `iat` has one-second resolution**, so a token minted in the same second as a password change was rejected as "older". Real bug in my own Phase 17 work — added a 1-second tolerance in `authenticate.middleware.js`.

## Behaviours deliberately NOT changed (documented instead)
- **`createTask` re-checks project membership in the service**, so the documented `requireProjectPermission` workspace-admin bypass is ineffective for task creation — while the project dashboard (middleware-only) does honour it. Two layers disagree. Changing either would widen or narrow access, so both were left alone and pinned by tests.
- **`POST /subtasks` returns the PARENT TASK under the `subtask` key** (PATCH returns the subtask). Inconsistent, but fixing it is a breaking response change.
- **Archived projects stay retrievable by id** (`getProjectById` does not filter `isArchived`), unlike tasks which 404 when archived.
- Only `User` and `Workspace` define a `toJSON` `_id`→`id` transform; every other resource serializes as `_id`.

- `eslint` 0 errors (6 pre-existing warnings); `prettier --check` clean.
- Temp harnesses deleted; the `E:/mongodb-binaries` directory I created was removed.

# 2026-09-17 (later) — Phase 19 investigation: the authorization inconsistency

**Analysis only. No source file was modified** (confirmed via `git status`).

## Method
Rather than reading alone, I ran an empirical probe: a workspace **admin** who is deliberately **not** a project member attempted all 44 project-scoped routes, with fixtures rebuilt before each route (some routes archive the project and would poison the rest). Rejections were attributed to a layer by message:
- middleware → "You do not have permission to perform this action" / "You are not a member of this project"
- service → "You must be a project member" / "You can only delete your own …"

Then the same sweep ran for a plain workspace **member** as a contrast.

## Result (workspace admin, not a project member)
- **34 ALLOWED**, 4 not-found (fixture artifacts), 1 validation, **4 DENIED BY SERVICE**.
- Workspace member: only **4 read routes** reachable; everything else denied by the middleware.

**The 4 genuine conflicts** — middleware says yes, service says no:
| Route | Permission | Service message |
|---|---|---|
| `POST /tasks` | `task:create` | "You must be a project member to create a task" |
| `POST /tasks/:taskId/subtasks` | `subtask:create` | "You must be a project member" |
| `PATCH /tasks/:taskId/subtasks/:subtaskId` | `subtask:update` | "You must be a project member" |
| `DELETE /tasks/:taskId/subtasks/:subtaskId` | `subtask:delete` | "You must be a project member" |

## Correction to my earlier static read
`assignTask` is **not** a conflict. Its check at `task.service.js:493` tests the **assignee**, returning **400** "Assignee must be a project member" — data validation, not caller authorization. Same for the check at `:42` in `createTask`. The probe caught this; reading alone had mis-attributed it.

## The predicate is triplicated
`hasPermission(role, UPDATE_WORKSPACE)` — the definition of "workspace elevated" — is written in **three** places:
1. `requireProjectPermission.middleware.js:38` (bypass)
2. `taskComment.controller.js:61` → passes `isWorkspaceElevated` into the service
3. `attachment.controller.js:138` → same

So an **established pattern already exists** for Policy A: controller derives elevation, service honours it. `createTask`/subtask services simply don't follow it — the task controller passes no such flag.

## Third, deliberate rule (not the same conflict)
`assertCommentOwner` (`taskComment.service.js:80-84`) is **author-only by design** — the comment explicitly states no project or workspace role may override it. So a workspace admin can *delete* another user's comment but not *edit* it. Intentional, but a third distinct rule worth knowing about.

## Layers that agree already
`assertCanDeleteComment` and `assertCanDeleteAttachment` both accept `isWorkspaceElevated` and honour the bypass → consistent with the middleware.

## Structural note
Project **lifecycle** routes (update/archive/restore/status, add/remove project member) are gated by `ws:UPDATE_WORKSPACE`, **not** `requireProjectPermission`. But `PATCH .../members/:userId/role` uses `proj:project:change_role`. So within project-membership management, adding/removing needs workspace admin while changing a role needs project admin. Worth flagging separately.

Also: **reads are workspace-scoped** (any workspace member can read any project's tasks/subtasks), writes are project-scoped. That looks deliberate.

## Consequence for Policy B worth flagging
Under strict "project membership always required", `POST .../members` is itself gated by `ws:UPDATE_WORKSPACE`. Requiring project membership to add a project member is circular — a workspace admin could not add themselves, and a project whose owner leaves could become unmanageable. Policy B needs a deliberate exception for member management.

## Scope of change per policy
- **Policy A** — 4 service functions gain an `isWorkspaceElevated` parameter (default false) + 4 controller call sites, mirroring the existing comment/attachment pattern. No route, constant or schema change. Optionally extract the triplicated predicate into one helper.
- **Policy B** — remove the bypass from `requireProjectPermission`, then also strip `isWorkspaceElevated` from the 2 controllers + 2 service signatures, and add project-level guards to ~6 lifecycle routes that currently rely on `ws:UPDATE_WORKSPACE` alone. Larger, and changes routes.

User was asked to choose the policy; decision still open. **Nothing implemented.**

# 2026-09-17 (later still) — Phase 19: Policy A implemented

**User chose Policy A** — workspace owner/admin hold project-level authority.

## The change (small, as scoped)
1. **Single-sourced the predicate.** New `hasProjectOverride(workspaceRole)` in `src/constants/rolePermissions.js` — the one definition of "workspace elevated". It borrows `UPDATE_WORKSPACE` deliberately rather than declaring a new constant, so the workspace role table stays the source of truth.
2. **Three existing call sites now use it:** `requireProjectPermission.middleware.js`, `taskComment.controller.js`, `attachment.controller.js` (the latter two previously re-derived it by hand).
3. **Four task services honour it:** `createTask`, `createSubtask`, `updateSubtask`, `deleteSubtask` take `isWorkspaceElevated = false` (appended last, matching the existing comment/attachment pattern) and skip the caller-membership guard when true.
4. **`task.controller.js` computes and passes it** in the four handlers, mirroring the comment/attachment controllers.

**No route, permission-constant, schema or migration change.** Exactly the scope predicted.

## Deliberately NOT touched
- `assignTask`'s check at `task.service.js:504` — that validates the **assignee** is a project member (400), not the caller. Left alone.
- `createTask`'s assignee check (same reason).
- `assertCommentOwner` — editing is author-only; the workspace override does not apply, by design.
- The 7 `requireWorkspacePermission(UPDATE_WORKSPACE)` route guards on project lifecycle — that is a *different* check (workspace-level permission), not the project override.

## Residual notes

- The pre-existing oddity remains: `POST`/`DELETE .../projects/:projectId/members` require `ws:UPDATE_WORKSPACE` while `PATCH .../members/:userId/role` requires `proj:project:change_role`. Untouched — out of scope, but worth revisiting.

# 2026-09-17 (final) — Phase 19: API DOCUMENTATION

## Approach: generate, don't hand-write
The old `docs/API.md` was an early-phase stub listing endpoints that **do not exist**
(`/api/projects`, `/api/tasks`). Rather than hand-write a replacement that would drift,
the docs are **derived from the implementation and then verified against it**.

### New scripts (`server/scripts/`)
- **`route-inventory.js`** — parses every `src/routes/*.routes.js`, resolves mount prefixes
  from `index.routes.js`, and emits method + full path + guard chain + validator + controller.
  Also parses **inline routes on the index router** (see the bug below).
- **`openapi-operations.js`** — per-route metadata: tag, summary, returned resource.
  One entry per route; the build **fails** if a route has none.
- **`generate-openapi.js`** — assembles `docs/openapi.json`. Request bodies and query
  parameters come from the route's own Zod validator via **`z.toJSONSchema`** (Zod 4), so
  they cannot drift. Error responses are inferred from the guard chain (401 if
  authenticated, 403 if a permission guard, 404 if a path param).
- **`verify-docs.js`** — checks route coverage both ways, `$ref` integrity, and that each
  operation's `security` matches its guard chain. Exits non-zero on drift.

### Artifacts
- `docs/API.md` — rewritten from scratch. All 31 requested topics, endpoint tables per
  resource, role/permission matrices, worked `curl` examples, status codes, upload rules.
- `docs/openapi.json` — OpenAPI 3.1, **81 operations across 61 paths, 45 schemas**.
- `README.md` (repo root) — rewritten: description, features, stack, setup, scripts, folder
  structure, docs location, testing, deployment notes.
- `docs/README.md` — corrected its fake endpoint list (it claimed `/api/projects`).
- `src/routes/docs.routes.js` — serves the spec at `GET /api/v1/openapi.json`, cached,
  returns 503 with guidance if the artefact is missing.

### npm scripts added
`docs:generate`, `docs:verify`, `routes`.

## Bug found by the verification (the point of building it)
`GET /api/v1/` and `GET /api/v1/health` are declared **directly in `index.routes.js`**, not in
a `*.routes.js` file. The inventory only scanned the latter, so both were silently absent from
the spec — and `verify-docs` did not complain, because it compares the spec against the same
incomplete inventory. Fixed by parsing inline index routes too: **79 → 81 routes**.
Lesson: a verifier that shares a blind spot with the thing it verifies proves nothing.

## Other fixes during the phase
- ESLint only globbed `**/*.js`, so the new `.mjs` scripts produced 27 `no-undef` errors.
  Renamed them to `.js` (the codebase is uniformly `.js` with `"type": "module"`) rather than
  widening the shared config.
- `preserve-caught-error`: added `{ cause }` to a re-thrown error in the generator.

## Verification
- **243 tests / 243 pass** (unchanged — no runtime behaviour touched beyond the docs route).
- `eslint` **0 errors** (6 pre-existing warnings); `prettier --check` clean.
- `npm run docs:verify` → **81 routes in code = 81 operations documented**, 509 refs resolve.
- Cross-checked every `/api/v1/...` path mentioned in `docs/API.md`, `docs/README.md` and
  `README.md` against the real route table — all exist.

## Notable facts captured in the docs
- Only `User` and `Workspace` remap `_id` → `id`; everything else serialises `_id`.
- `PATCH /workspaces/:id/archive` and `/restore` require workspace role **OWNER**, which is
  stricter than the `archive_workspace` permission granted to admins. Route wins.
- `POST /subtasks` returns the parent task under the `subtask` key.
- An archived project stays retrievable by id; an archived task 404s.
- Comment **editing** is author-only and no role overrides it; **deleting** honours moderation.

## Remaining gaps
- `docs/ARCHITECTURE.md`, `DATABASE.md`, `SECURITY.md`, `FEATURES.md`, `SETUP.md`,
  `ENVIRONMENT.md`, `VISION.md`, `CHANGELOG.md` are still early-phase and were left untouched.
- Response schemas are hand-authored from the models; only *request* schemas are generated.
  A response-shape change would not be caught automatically.
- No Swagger UI page (deliberately — avoids a CDN dependency and a relaxed CSP).
  The spec is importable into any OpenAPI tooling.
- `ROADMAP.md` Phase 19 status not updated (docs-only file, left alone).

# 2026-09-17 (Phase 20) — PRODUCTION DEPLOYMENT

Written up after the fact: this phase was implemented between 20:12 and 20:58 but the session
ended before it was logged or committed. **It is still uncommitted** — `HEAD` is `40b3071`.

## What was built
- **`Dockerfile`** — multi-stage (`deps` → `runtime`). Build toolchain (python3/make/g++) only in
  `deps` so the native `bcrypt` build never ships. Runs as the unprivileged `node` user,
  `dumb-init` as PID 1 to reap zombies, `HEALTHCHECK` pointing at **liveness only**.
  `/app/src/uploads` declared as a `VOLUME`.
- **`docker-compose.yml`** — `api` + `mongo:7`. Required variables use `:?` so compose fails
  immediately instead of starting with an empty secret. `mongo` healthcheck gates the API's
  start. `stop_grace_period: 20s` deliberately exceeds `SHUTDOWN_TIMEOUT_MS` (10s), otherwise
  Docker SIGKILLs mid-drain and the graceful path never completes.
- **`.dockerignore`** — the important entry is `.env`: an image layer is readable by anyone who
  can pull the image, so a deleted-but-copied secret is still leaked.
- **Health probes** (`src/routes/health.routes.js`) — `GET /api/v1/health` (liveness, never
  touches the database) and `GET /api/v1/health/ready` (readiness; bounded 2s ping, 503 when
  down). Mounted in `app.js:136`, **ahead of** the rate limiter at `:139`, so a busy period
  cannot throttle a probe. Successful probes are excluded from access logs.
  Readiness builds its body by hand rather than with `ApiResponse`, which hardcodes
  `success: true` — reporting success next to a 503 would be a lie.
- **`src/utils/logger.js`** — one JSON object per line in production; `morgan` writes into it.
- **`src/config/paths.js`** — `PROJECT_ROOT` / `DOCS_DIR`, so paths do not depend on `cwd`.
- **`scripts/preflight.js`** — checks the things that are *legal* but wrong for production
  (placeholder secret, localhost database, empty CORS, `TRUST_PROXY=0`). Reads only
  `process.env` and never prints a secret — only its length and a verdict. Wired into
  `start:prod`. Verified: correctly exits 1 against the development `.env`.
- **`docs/DEPLOYMENT.md`** (new, ~21 KB) — architecture, env vars, three deploy paths
  (Docker / platform / systemd), migrations, health checks, production checklist, and a
  **Known limitations** section that states the real constraints plainly.
- `gracefulShutdown.js`, `database.js`, `env.js`, `error.middleware.js`, `.env.example` and
  both `README.md`s reworked. `health.test.js` + `api-contract.test.js` added → **254 tests**.

## Completed this session — the format gate was red
`npm run format:check` was failing on **5 files**. More importantly, it was already failing at
`HEAD`: `git show HEAD:server/docs/openapi.json` fails prettier, so the Phase 19 claim of
"`prettier --check` clean" **was not true**. The generated spec was committed in
`JSON.stringify` form (every array expanded), which prettier collapses.

Root cause fixed rather than papered over: **`generate-openapi.js` now formats its own output**
via `prettier.resolveConfig(OUTPUT)` + `prettier.format(..., { parser: 'json' })`. The import is
deliberately optional (dynamic `import` in a `try`) because the production image ships `scripts/`
for the preflight but installs with `--omit=dev`, so prettier is absent there — the script still
works, just without tidying. Verified idempotent: two consecutive `docs:generate` runs produce
byte-identical output (same md5), so the generator and the gate can no longer disagree.

Also fixed: **11 stale `.mjs` references** across the four doc scripts — Phase 19 renamed them to
`.js` but left the comments and, worse, the generator's error message telling the reader to edit
`scripts/openapi-operations.mjs`, a file that does not exist. And `route-inventory.js` pointed at
`docs/openapi.yaml` (the artefact is `openapi.json`).

Then formatted `docs/API.md`, `docs/DEPLOYMENT.md`, `package.json`, `package-lock.json`. The
markdown changes are table-column padding only — the ASCII diagrams live in code fences and are

## A second, independent cause of the same broken gate
With the files formatted, `npm run format:check` was green — **in this working copy only.**
`core.autocrlf` is `true` on this machine and there was no `.gitattributes`, so git rewrites
every text file to CRLF on checkout while `.prettierrc` demands `endOfLine: "lf"`.

Verified rather than assumed: cloning the repo to a temp directory and running prettier against
the clone reported **"Code style issues found"** for `app.js` and `docs/API.md` — files that are
correctly formatted in the repository. So the gate would have failed for anyone who cloned on
Windows, which is exactly the kind of false alarm that trains people to ignore a gate.

Fixed with a root **`.gitattributes`** (`* text=auto eol=lf`, binaries declared explicitly,
Windows-only script types pinned to CRLF). `git add --renormalize .` changed **nothing**, which
confirms the stored blobs were already LF — the fix only affects future checkouts, so no churn.
Re-verified: a fresh clone now passes `prettier --check` across the whole `server/` tree.
