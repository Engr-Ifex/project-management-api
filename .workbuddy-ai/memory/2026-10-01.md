### 7 · Projects — edit + settings surface  ✅

all. Added a **Settings tab** to `ProjectOverview` (`ProjectSettingsTab.tsx`):
name, description, deadline, colour, plus an "At a glance" panel.

Two things worth keeping:
- **Editing a project is a *workspace* operation.** A project owner cannot
  rename their own project; a workspace owner/admin can rename any project in
  the workspace (deliberate — `API-INTEGRATION.md` §15, `hasProjectOverride`).
  The form gates on `can.manageProjects`, **not** the project role, and says so
  in the UI when the caller cannot edit.
- Clearing is `null`, not omission: `deadline` and `color` are `.nullable()` in
  the validator, and omitting a key means "leave it alone" everywhere else in
  this API. `projectsApi.update`'s body type was widened to `string | null` to
  match — the type was lying before.
- `deadline` must be a full ISO **datetime** (`.datetime()`), so the date input
  is converted with `T00:00:00.000Z`.

### 14 · Search / filters — the three unused filters + URL sync  ✅
`projectTasksQuery` already accepted `assignee`, `labels`, `dueDateFrom/To`,

## `PATCH /projects/:id` returns 400 in this harness — NOT an app bug

Every project update failed with `Path createdBy is required`. Root cause is the
**in-process store**, not the service:

- `updateProjectStatus` is a plain `findOne` + mutate + `save()`, which cannot
  drop an untouched field on real Mongoose.
- `createProject` sets `createdBy` correctly, and a freshly created project
  updates fine (200).
- `memoryStore.js`'s own comments document this exact bug class ("a later
  `save()` persisted a user that had lost its email and name"), and `persist`
  merges `doc.toObject()`, so an explicit `createdBy: undefined` overwrites the
  stored value.
- Reproduction: created → `createdBy` set, update 200; after `PATCH /status` →
  `createdBy` null; after `POST /labels` → update 400.

**Do not "fix" the backend for this.** Verify project editing against a
*newly created* project, not a seeded one.

## 12 · Activity — avatars, descriptions, links, grouping  ✅

Was `Name` + `humaniseEnum(action)` + a timestamp, i.e. it said
"task_status_changed" to a human and never named the thing that changed. The
metadata had carried the useful part all along (previous status, label name,
filename) — it was simply not read.

- `lib/activity.ts` — `describeActivity` maps action + metadata to a sentence, a
  resource name and an href. **`ActivityAction` is an open union
  (`(string & {})`), so every action falls through to `humaniseEnum`**: a new
  server action must degrade to a readable label, never a blank row.
- Metadata shapes worth remembering: `task_created`/`task_archived`/
  `task_restored` carry `taskTitle`; **`task_comment_*` and `subtask_*` carry only
  `taskId`**. A sentence built as "commented on" + title therefore trailed off
  into nothing — hence the `withTask` helper, which drops the preposition and
  moves the noun into the text ("commented on a task") when the title is absent.
- `task_updated` has two shapes: multi-field (`fields`) and single-field
  (`field`/`from`/`to`). The single-field form names the field, so it is
  preferred.
- `groupByDay` (in `lib/notifications.ts`) was made **generic over
  `{ createdAt: string }`** so the activity feed groups the same way. One
  implementation, no drift.
- Filter + page moved into the query string (`aPage`, `aLimit`, `aAction` —
  prefixed to avoid colliding with TasksTab's params on the same URL).

Verified: 15 entries, all links, avatars present, sentences read "Ada Owner
commented on a task" / "added the label Frontend".

## 13 · Attachments — PARTIAL

**Done and verified:**
- **Per-type icons** (`lib/attachments.ts` + `FileTypeIcon`) replacing the one
  generic paperclip. Kind comes from the **extension only** — the server checks
  magic bytes, but the client has nothing but the name until it downloads, and
  pretending otherwise would mean fetching every row.
- **Image thumbnails**, fetched through the authenticated blob path. The blob URL
  is revoked on unmount *and* on path change; a blob URL pins its whole file in
  memory for the document's lifetime, and a table of images would otherwise
  accumulate one per row forever.
- **Upload progress** — `uploadWithProgress` in `lib/api/client.ts` uses
  **XMLHttpRequest**, the only browser API with `upload.onprogress`; `fetch`
  cannot report upload progress at all. Everything else stays on `fetch`. The
  helper mirrors `request`'s session and error contract (cookie sent explicitly,
  401 broadcast, non-2xx → `ApiError` with the server's message).
- **Task-level attachments** — `TaskAttachments` mounted in `TaskDetail`.
  `listForTask`/`uploadToTask` had existed unused since the beginning.
  **Deletion uses the project-scoped endpoint** — it is the only one the API
  exposes, and it resolves the attachment by id within the project.

Verified: project tab shows 5 rows with kinds `pdf`/`spreadsheet`/`pdf` and 2
image previews; the task page shows its own two files.

**Not done: comment-level attachments.** `listForComment`/`uploadToComment`

## 8 · Tasks — scheduling fields DONE, decomposition NOT done

**Due date, start date and estimated time are now all editable**, and start date
did not exist at all before.

- **No new endpoint was needed.** `updateTaskSchema` already accepts `startDate`,
  `dueDate` **and** `estimatedTime`, so one `PATCH /tasks/:taskId` covers all
  three. That is why `setDueDate`/`setStartDate` are *still* unused — not an
  oversight: one request beats three, and it is the shape the schema supports.
  (Note `TaskDetail` already had a `setSchedule`-shaped gap; the client's
  `tasksApi.update` body type already carried all three fields.)
- Cleared dates send `null`, not an omitted key — omission means "leave it
  alone" everywhere in this API, so a cleared date would silently survive.
- The estimate commits on **blur**, not per keystroke (a request per digit), and
  is **uncontrolled + keyed on the stored value**: a controlled field would need
  syncing back from the server on every response.

Verified end to end: `startDate = 2026-11-01`, `dueDate = 2026-11-30`,
`estimatedTime = 240`, all confirmed by re-reading the task from the API.

### Harness: headless Chrome does not focus the document by default

This cost real time. `el.focus()` is a **silent no-op** in headless Chrome unless
focus emulation is on, so `document.activeElement` stays `BODY`, `el.blur()`
never fires, and **every `onBlur` handler is untestable** — which looks exactly
like a broken field. The estimate appeared not to save for two runs because of
it. Fixed with `Emulation.setFocusEmulationEnabled { enabled: true }` at startup
in `ws-switch.mjs`.

New harness actions: `--act "blur:<js>"`, and `--key "<js>|Enter"`.

### Method that made this safe — worth reusing

`tsc` runs with `noUnusedLocals`, so **after replacing a block with a component
call it lists every declaration the extraction orphaned**, by line number. That
turned "find the dead code" from a hunt into a checklist. Sequence:
1. Read the block, write the component.
2. Replace the line range with a Python splice that **asserts the first and last
   lines before touching anything** (a stale range silently corrupts the file).
3. Add the import, run `tsc`, delete exactly what it names.
4. Verify the feature in the browser, not just that it compiles.

Deleting bottom-up keeps earlier indices valid when removing several ranges in
one pass.
